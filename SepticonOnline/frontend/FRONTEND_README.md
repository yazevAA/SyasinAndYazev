
# SEPTIKON ONLINE
# Руководство по разработке Frontend

## 1. Назначение документа

Данный документ предназначен для разработчика клиентской части проекта Septikon Online.

Backend проекта разрабатывается отдельно на языке Go.

Задача Frontend-разработчика — создать пользовательский интерфейс браузерной версии игры, обеспечить взаимодействие с сервером и корректно отображать полученное игровое состояние.

Frontend должен работать с существующим Backend через HTTP API и обмениваться данными в формате JSON.

## 2. Общая информация о проекте

Septikon Online — браузерная версия настольной стратегической игры Septikon.

В игре участвуют два игрока. Каждый игрок управляет собственной станцией, состоящей из подземных уровней и поверхности.

Основные элементы игры:

- игровые комнаты;
- игроки;
- игровые станции;
- отсеки;
- ресурсы;
- роботы;
- ракеты;
- производственные задачи;
- ремонтные задачи;
- очередность ходов.

Пользователь должен иметь возможность создать комнату, пригласить второго игрока, увидеть игровое поле и выполнять доступные игровые действия.

## 3. Рекомендуемые технологии

Для реализации Frontend рекомендуется использовать:

- React — создание пользовательского интерфейса;
- TypeScript — типизация данных и компонентов;
- Vite — сборка и запуск проекта;
- CSS или CSS Modules — оформление интерфейса.

Данный стек является предложением команды, а не обязательным требованием задания по Go.

Если разработчик уже использует другой совместимый стек, его можно согласовать с командой.

## 4. Подключение к Backend

Локальный адрес Backend:

http://localhost:8080

Проверка доступности:

GET /health

Для Frontend рекомендуется использовать переменную окружения:

VITE_API_BASE_URL=http://localhost:8080

Она должна находиться в файле .env.

Не рекомендуется прописывать адрес Backend непосредственно в нескольких компонентах.

Если Backend запускается на другом компьютере, необходимо указать его сетевой адрес.

Например:

VITE_API_BASE_URL=http://192.168.1.100:8080

Это только пример. Нужно использовать фактический адрес компьютера, на котором работает сервер.

## 6. Назначение основных папок

### api

Здесь располагается код для взаимодействия с Backend.

client.ts:
- общий HTTP-клиент;
- базовый адрес сервера;
- обработка ошибок;
- отправка JSON;
- получение JSON.

rooms.ts:
- получение списка комнат;
- создание комнаты;
- получение конкретной комнаты;
- подключение второго игрока.

game.ts:
- бросок кубика;
- перемещение робота;
- начало ремонта;
- завершение хода.

### components

Здесь располагаются повторно используемые элементы интерфейса.

common:
- кнопки;
- окна;
- индикаторы загрузки;
- сообщения об ошибках.

board:
- игровое поле;
- уровни;
- отсеки;
- поверхность станции.

player:
- карточка игрока;
- ресурсы;
- информация о станции.

robot:
- отображение роботов;
- выбор робота;
- отображение позиции.

rocket:
- отображение ракет;
- состояние ракет.

game:
- информация о ходе;
- кубик;
- игровые действия;
- панель управления.

### pages

Здесь располагаются основные страницы приложения.

MainPage:
Главная страница и начальное меню.

LobbyPage:
Список доступных комнат и создание новой комнаты.

WaitingRoomPage:
Экран ожидания второго игрока.

GamePage:
Основной игровой экран.

### types

Здесь описываются TypeScript-типы данных, получаемых от Backend.

Типы необходимо составлять по фактическим JSON-тегам Go-структур.

Не следует самостоятельно придумывать поля, которых нет в ответах сервера.

## 7. Этапы разработки

### Этап 1. Создание проекта

Необходимо:
1. Создать Frontend-приложение.
2. Настроить TypeScript.
3. Настроить Vite.
4. Создать структуру папок.
5. Добавить переменную окружения для Backend.
6. Проверить запуск приложения.

На этом этапе игровую логику реализовывать не нужно.

### Этап 2. Подключение к Backend

Создать общий API-клиент.

Реализовать:
- проверку доступности сервера;
- получение списка комнат;
- создание комнаты;
- подключение игрока;
- получение информации о комнате.

Проверить, что Frontend корректно обрабатывает успешные ответы и ошибки.

### Этап 3. Главное меню и комнаты

Создать:
- главное меню;
- кнопку создания комнаты;
- список доступных комнат;
- форму имени игрока;
- экран ожидания второго игрока.

После создания комнаты необходимо сохранить её ID для последующего обращения к Backend.

Способ формирования playerId нужно согласовать с Backend-разработчиком.

### Этап 4. Получение состояния игры

Реализовать получение актуального состояния комнаты.

Основной маршрут:

GET /api/rooms/{roomId}

Полученные данные должны использоваться для построения игрового интерфейса.

До получения второго игрока необходимо корректно показывать состояние ожидания.

### Этап 5. Игровое поле

Необходимо реализовать отображение двух станций.

Каждая станция содержит:

- 8 подземных уровней;
- 21 отсек на каждом подземном уровне;
- поверхность, обозначаемую уровнем 9.

Важно:

Геометрия игрового поля должна соответствовать оригинальному полю Septikon и предоставленным правилам.

Нельзя заменять исходную раскладку произвольной сеткой, если она отличается от оригинала.

На поле необходимо отображать:
- типы отсеков;
- повреждения;
- роботов;
- ракеты и другие игровые объекты, если их состояние передано сервером.

### Этап 6. Игровая информация

Добавить:
- имена игроков;
- ресурсы;
- текущий номер хода;
- текущего игрока;
- результат броска кубика;
- доступность основного действия;
- состояние производства;
- состояние ремонта;
- состояние ракет.

Все значения должны браться из Backend.

### Этап 7. Игровые действия

Подключить подтверждённые маршруты:

- бросок кубика;
- перемещение робота;
- начало ремонта;
- завершение хода.

Запуск ракеты подключить после подтверждения точного маршрута и JSON-формата.

После успешного выполнения команды необходимо обновлять состояние комнаты.

### Этап 8. Синхронизация

WebSocket пока не реализован.

Для первой версии использовать периодическое получение состояния комнаты.

Рекомендуемый интервал:

1–2 секунды.

Необходимо:
- не допускать перекрытия запросов;
- останавливать обновление при выходе из комнаты;
- обрабатывать потерю соединения;
- обновлять состояние после игровых действий.

В будущем polling можно заменить WebSocket после его реализации на Backend.

## 8. Принципы работы с игровым состоянием

Backend является единственным источником достоверного игрового состояния.

Например, при перемещении робота:

1. Пользователь выбирает робота.
2. Пользователь выбирает маршрут.
3. Frontend отправляет запрос Backend.
4. Backend проверяет допустимость действия.
5. Backend изменяет состояние игры.
6. Frontend получает обновлённое состояние.
7. Интерфейс отображает новую позицию робота.

Frontend не должен считать, что действие выполнено, до получения успешного ответа сервера.

## 9. Обработка ошибок

Нужно предусмотреть следующие ситуации:

- Backend не запущен;
- потеря соединения;
- комната не найдена;
- игрок не может подключиться;
- игрок пытается выполнить недопустимое действие;
- сервер возвращает ошибку;
- данные не удалось обработать.

Ошибки должны отображаться понятным пользователю способом.

Не следует показывать пользователю необработанный технический ответ сервера, если его можно представить понятным сообщением.

## 10. Требования к интерфейсу

Интерфейс должен быть:
- понятным;
- удобным;
- визуально соответствовать тематике Septikon;
- адаптированным под разрешение экрана;
- разделённым на логические компоненты.

Особое внимание уделить игровому полю.

Игрок должен быстро понимать:
- где находится его станция;
- где находится станция противника;
- какие отсеки доступны;
- где находятся роботы;
- какие ресурсы имеются;
- чей сейчас ход;
- какое действие можно выполнить.

## 11. Что не нужно реализовывать самостоятельно

Не нужно дублировать на Frontend:

- генерацию результата кубика;
- серверную проверку ходов;
- правила перемещения роботов;
- расчёт изменения ресурсов;
- продвижение производства;
- продвижение ремонта;
- продвижение ракет;
- определение победителя.

Эти операции выполняет Backend.

Frontend может показывать подсказки и предварительно блокировать недоступные элементы интерфейса, но серверная проверка остаётся обязательной.

## 12. Критерии готовности Frontend

Первый этап можно считать завершённым, когда:

- [ ] Приложение запускается.
- [ ] Frontend подключается к Backend.
- [ ] Работает проверка доступности сервера.
- [ ] Отображается список комнат.
- [ ] Можно создать комнату.
- [ ] Второй игрок может подключиться.
- [ ] Работает экран ожидания.
- [ ] Получается состояние комнаты.
- [ ] Отображаются две станции.
- [ ] Игровое поле соответствует оригинальной схеме.
- [ ] Отображаются игроки и ресурсы.
- [ ] Отображаются роботы и игровые задачи.
- [ ] Отображается текущий ход.
- [ ] Работают подтверждённые игровые действия.
- [ ] После действий интерфейс получает обновлённое состояние.
- [ ] Обрабатываются ошибки и потеря соединения.

## 13. Взаимодействие с Backend-разработчиком

Если для реализации интерфейса не хватает данных или API-маршрута, необходимо:

1. Описать, какую функцию нужно реализовать.
2. Указать, какие данные должны передаваться.
3. Указать, какой ответ необходим Frontend.
4. Передать запрос Backend-разработчику.
5. Согласовать изменение API.
6. Обновить документацию.

Не следует самостоятельно придумывать API-маршруты и ожидать, что Backend автоматически их поддерживает.

## 14. Главное правило проекта

Frontend отвечает за отображение и взаимодействие с пользователем.

Backend отвечает за правила и состояние игры.

Все игровые изменения должны проходить через Backend.
