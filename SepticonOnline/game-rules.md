
# SEPTIKON ONLINE
# Описание игрового поля и игровых объектов для Frontend

## 1. Назначение документа

Документ содержит описание основных игровых объектов, которые должны отображаться в пользовательском интерфейсе Septikon Online.

Он предназначен для Frontend-разработчика и помогает понять структуру игрового поля, станции, ресурсов, роботов, ракет и игровых процессов.

Все игровые данные должны поступать от Backend.

Frontend отвечает за их визуальное представление.

## 2. Общая структура игры

В одной игровой комнате участвуют два игрока.

Каждый игрок управляет собственной станцией.

Основные объекты игры:

- игровая комната;
- два игрока;
- две станции;
- подземные уровни;
- поверхность станции;
- отсеки;
- ресурсы;
- роботы;
- ракеты;
- производственные задачи;
- ремонтные задачи;
- очередь ходов.

## 3. Структура станции

Станция состоит из восьми подземных уровней и поверхности.

Подземные уровни:

1. Уровень 1.
2. Уровень 2.
3. Уровень 3.
4. Уровень 4.
5. Уровень 5.
6. Уровень 6.
7. Уровень 7.
8. Уровень 8.

На каждом подземном уровне располагается 21 отсек.

Поверхность обозначается уровнем 9 и учитывается отдельно.

Таким образом, Frontend должен отображать:

- 8 подземных уровней;
- по 21 отсеку на каждом подземном уровне;
- поверхность станции.

Важно:

Поверхность не следует автоматически считать обычным подземным уровнем с 21 отсеком. Её визуальное представление должно соответствовать правилам и исходному изображению игрового поля.

## 4. Идентификаторы отсеков

Каждый отсек имеет собственный идентификатор.

Формат:

L{level}-C{position}

Где:

L — номер уровня.

C — номер позиции на уровне.

Примеры:

L1-C1
L1-C2
L1-C21
L2-C7
L8-C21

Нумерация уровней и позиций начинается с 1.

Важное замечание для TypeScript:

Индексы массивов начинаются с 0, но игровые координаты начинаются с 1.

При отображении необходимо учитывать это различие.

## 5. Типы отсеков

В Backend известны следующие типы:

### unknown

Неизвестный или ещё не определённый тип отсека.

Frontend должен отображать его в соответствии с игровыми правилами.

### production

Производственный отсек.

Связан с производственными процессами и получением ресурсов.

### combat

Боевой отсек.

Относится к боевой части станции.

### energy

Энергетический отсек.

Связан с энергетикой станции.

### resource

Ресурсный отсек.

Связан с ресурсами станции.

### rocket

Отсек, связанный с ракетами.

### command

Командный отсек.

Связан с управлением станцией.

Визуальное оформление каждого типа следует согласовать с оригинальным игровым полем.

Не следует придумывать игровые эффекты, характеристики или ограничения, которые не подтверждены правилами и Backend.

## 6. Состояние отсеков

Известные поля отсека:

- id — идентификатор отсека;
- level — номер уровня;
- position — номер позиции;
- type — тип отсека;
- damaged — признак повреждения.

Frontend должен отображать тип отсека и его состояние.

Если damaged имеет значение true, интерфейс должен визуально показывать повреждение.

Если damaged имеет значение false, отсек отображается как неповреждённый.

Точное оформление повреждений является задачей интерфейса, но их игровое значение определяется Backend.

## 7. Игрок

Игрок — участник игровой комнаты.

Известные данные игрока:

- id;
- name;
- ready;
- station;
- inventory;
- robots;
- productionTasks.

Назначение:

id — идентификатор игрока.

name — имя игрока.

ready — состояние готовности, если оно используется текущей версией Backend.

station — игровая станция.

inventory — инвентарь игрока.

robots — список роботов.

productionTasks — список производственных задач.

Окончательную структуру необходимо сверить с Go JSON-тегами.

## 8. Ресурсы

В игре используются следующие типы ресурсов:

- metal — металл;
- uranium — уран;
- oxygen — кислород;
- biomass — биомасса;
- energy — энергия.

Frontend должен отображать количество каждого ресурса.

Рекомендуется создать отдельный компонент для отображения ресурсов игрока.

Например:

Ресурсы игрока:

Металл: значение из Backend

Уран: значение из Backend

Кислород: значение из Backend

Биомасса: значение из Backend

Энергия: значение из Backend

Числа в интерфейсе должны обновляться после получения нового состояния комнаты.

Не следует самостоятельно изменять количество ресурсов при нажатии кнопок.

## 9. Роботы

Роботы являются игровыми объектами, которые могут находиться на станции и перемещаться по игровому полю.

Известные поля робота:

- id;
- ownerId;
- position;
- active.

Назначение:

id — идентификатор робота.

ownerId — идентификатор владельца.

position — текущая позиция.

active — состояние активности.

Позиция содержит:

- level;
- position.

Frontend должен отображать робота на соответствующем отсеке или поверхности в зависимости от его координат.

Рекомендуется предусмотреть:

- визуальное выделение робота;
- выбор робота;
- отображение его позиции;
- отображение состояния активности.

Окончательная структура робота определяется фактическим JSON Backend.

## 10. Перемещение роботов

Для перемещения используется HTTP-запрос:

POST /api/rooms/{roomId}/game/move-robot

В запросе передаются:

- playerId;
- robotId;
- path.

path содержит последовательность игровых позиций.

Пример:

{
  "playerId": "player-1",
  "robotId": "robot-1",
  "path": [
    {
      "level": 1,
      "position": 1
    },
    {
      "level": 1,
      "position": 2
    }
  ]
}

Frontend может показывать выбранный путь и визуально выделять клетки.

Однако проверка допустимости перемещения выполняется Backend.

После успешного ответа необходимо получить актуальное состояние комнаты.

## 11. Производство ресурсов

В игре предусмотрены производственные процессы.

В Backend присутствует логика производственных задач и их продвижения.

Известные поля производственной задачи из предыдущих материалов проекта:

- id;
- resource;
- amount;
- requiredTurns;
- remainingTurns;
- completed;
- compartmentId.

Назначение:

id — идентификатор задачи.

resource — тип производимого ресурса.

amount — количество производимого ресурса.

requiredTurns — необходимое количество ходов.

remainingTurns — оставшееся количество ходов.

completed — признак завершения задачи.

compartmentId — идентификатор связанного отсека, если это поле присутствует в текущей JSON-структуре.

Важно:

Эти поля необходимо сверить с актуальными Go-структурами и JSON-тегами.

Frontend может отображать прогресс производства, но не должен самостоятельно рассчитывать его продвижение.

## 12. Ремонт

В игре присутствует механика ремонта повреждённых отсеков.

Backend поддерживает запуск ремонта и продвижение ремонтных задач.

Известные поля ремонтной задачи из предыдущих материалов:

- id;
- ownerId;
- compartmentId;
- remainingTurns;
- completed.

Frontend должен отображать информацию о ремонте, если она присутствует в полученном состоянии игры.

Запуск ремонта осуществляется через:

POST /api/rooms/{roomId}/game/repair

Пример:

{
  "playerId": "player-1",
  "taskId": "repair-task-1",
  "compartmentId": "L1-C1"
}

Frontend не должен самостоятельно снимать повреждение с отсека.

Это изменение выполняет Backend.

## 13. Ракеты

В Backend присутствует внутренняя логика ракет.

В предыдущих материалах проекта указывались следующие поля ракеты:

- id;
- ownerId;
- sourceStation;
- targetStation;
- position;
- totalDistance;
- speed;
- status.

Назначение:

id — идентификатор ракеты.

ownerId — владелец ракеты.

sourceStation — станция отправления.

targetStation — целевая станция.

position — текущая позиция ракеты.

totalDistance — общая дистанция.

speed — скорость.

status — состояние ракеты.

Ранее упоминались состояния:

- ready;
- flying;
- arrived.

Окончательные поля и значения необходимо сверить с текущей структурой Rocket и её JSON-тегами.

Frontend должен отображать состояние ракеты, полученное от Backend.

Не нужно самостоятельно продвигать ракету по дистанции.

## 14. Система ходов

В игре используется пошаговая система.

По текущей модели Backend:

- один бросок кубика за ход;
- одно основное действие за ход;
- основное действие требует предварительного броска;
- завершение хода требует выполнения броска и действия.

После завершения хода Backend продвигает игровые процессы:

- ракеты;
- производство;
- ремонт.

Frontend должен отображать:

- текущего игрока;
- номер хода;
- результат броска;
- состояние выполнения броска;
- состояние основного действия.

Точные названия JSON-полей необходимо сверить с актуальной структурой TurnManager.

Не следует определять текущего игрока по предположению, что он всегда находится первым в массиве игроков.

## 15. Игровая комната

Комната предназначена для двух игроков.

На начальном этапе в ней может находиться только один игрок.

В этом случае Frontend должен показывать экран ожидания.

После подключения второго игрока необходимо получить обновлённое состояние комнаты.

Известные статусы комнаты:

- waiting — ожидание игроков;
- playing — игра началась.

Точные значения и JSON-теги необходимо сверить с текущей структурой Room.

## 16. Отображение двух станций

Игровой интерфейс должен показывать обе станции.

Рекомендуется разделить интерфейс на две основные области:

1. Станция текущего игрока.
2. Станция противника.

Для каждой станции необходимо отображать:

- игровое поле;
- состояние отсеков;
- роботов;
- доступную информацию о ракетах;
- ресурсы владельца;
- задачи производства и ремонта, если они присутствуют в данных.

Расположение элементов интерфейса можно выбирать самостоятельно.

Но игровая геометрия должна соответствовать оригинальной схеме поля.

## 17. Важное правило обработки данных

Все игровые изменения должны выполняться через Backend.

Frontend не должен:

- самостоятельно генерировать результат кубика;
- менять ресурсы;
- завершать ремонт локально;
- продвигать ракеты;
- продвигать производство;
- самостоятельно переключать текущего игрока;
- считать недопустимое действие успешным.

Правильная последовательность:

1. Пользователь выполняет действие.
2. Frontend отправляет запрос.
3. Backend проверяет действие.
4. Backend изменяет состояние.
5. Frontend получает результат.
6. Frontend запрашивает актуальное состояние комнаты.
7. Интерфейс отображает обновлённые данные.

## 18. Главный принцип

Frontend должен максимально точно отображать состояние, которое передаёт Backend.

Если в структуре данных нет необходимого поля, его нельзя подменять выдуманным значением.

Если для отображения определённой механики не хватает API, необходимо согласовать расширение Backend.
