# Frontend Contract — Septikon Online

## 1. Назначение документа

Этот документ описывает правила взаимодействия Frontend с Backend проекта Septikon Online.

Он предназначен для Frontend-разработчика и позволяет работать с серверной частью без необходимости изучать исходный Go-код.

Документ содержит:

- описание API;
- доступные HTTP-маршруты;
- форматы запросов;
- структуру игровых объектов;
- назначение полей;
- правила выполнения действий;
- обработку ошибок;
- ограничения текущей реализации.

**Backend является источником истины для состояния игры.** Frontend отображает полученные данные и отправляет запросы на выполнение игровых действий.

---

## 2. Подключение к Backend

Локальный адрес сервера:

```text
http://localhost:8080
```

Все API-запросы отправляются относительно этого адреса.

Для запросов с JSON-телом необходимо использовать заголовок:

```http
Content-Type: application/json
```

Пример:

```http
POST http://localhost:8080/api/rooms
Content-Type: application/json
```

---

## 3. Важное замечание о JSON-полях

Backend написан на Go и использует стандартную сериализацию `encoding/json`.

В Go названия экспортируемых полей без специальных JSON-тегов обычно сохраняются в JSON с исходным написанием.

Например, Go-поле:

```go
PlayerID string
```

может передаваться в JSON как:

```json
{
  "PlayerID": "player-1"
}
```

а не как `playerID`.

Также некоторые поля могут иметь отдельные JSON-теги. Например, у игрового объекта поле `TurnManager` сериализуется под именем `turn`.

Поэтому при реализации Frontend необходимо ориентироваться на фактические JSON-ответы сервера. Не следует автоматически переводить все поля в `camelCase`.

В примерах ниже используются названия полей Go, если не указано иное.

# 4. Структура игровых объектов

## 4.1. Room — игровая комната

Комната создаётся первым игроком. Второй игрок подключается к уже существующей комнате.

| Поле | Тип | Описание |
|---|---|---|
| `ID` | string | Идентификатор комнаты |
| `Status` | string | Состояние комнаты |
| `Players` | RoomPlayer[] | Список подключённых игроков |
| `Game` | Game или null | Игровая партия, если она создана |

Возможные состояния:

- `waiting` — ожидание второго игрока;
- `playing` — партия создана и началась.

### RoomPlayer

| Поле | Тип | Описание |
|---|---|---|
| `ID` | string | Идентификатор игрока |
| `Name` | string | Имя игрока |

---

## 4.2. Game — игровая партия

Игровая партия создаётся после подключения второго игрока.

| Поле | Тип | Описание |
|---|---|---|
| `ID` | string | Идентификатор партии |
| `Status` | string | Состояние игры |
| `Players` | Player[] | Два участника партии |
| `Rockets` | Rocket[] | Список ракет |
| `TurnManager` | TurnManager | Менеджер ходов; в JSON поле называется `turn` |
| `WinnerID` | string | Идентификатор победителя, если определён |
| `Repairs` | RepairTask[] | Задачи ремонта, если поле присутствует в текущей реализации |

Возможные состояния игры:

- `waiting` — ожидание начала;
- `playing` — игра идёт;
- `finished` — игра завершена.

Важно: наличие и точное JSON-имя отдельных полей необходимо сверять с фактическим ответом сервера. В частности, `Repairs` должно присутствовать в структуре `Game` и не быть исключено из JSON.

---

## 4.3. TurnManager — менеджер ходов

Менеджер определяет очередность игроков и состояние текущего хода.

| Поле | Тип | Описание |
|---|---|---|
| `PlayerIDs` | string[] | Идентификаторы игроков в порядке очереди |
| `Turn` | Turn | Информация о текущем ходе |

Поле `TurnManager` в структуре игры имеет JSON-тег `turn`.

Внутреннее поле `Turn` при стандартной сериализации Go может называться `Turn`.

### Turn — состояние текущего хода

| Поле | Тип | Описание |
|---|---|---|
| `CurrentPlayerID` | string | ID игрока, который сейчас ходит |
| `Number` | number | Номер хода |
| `DiceResult` | number | Результат броска кубика |
| `DiceRolled` | boolean | Был ли уже брошен кубик |
| `ActionUsed` | boolean | Использовано ли основное действие |

Эти данные необходимы Frontend для управления доступностью кнопок и отображения текущего игрока.

---

## 4.4. Player — игрок

| Поле | Тип | Описание |
|---|---|---|
| `ID` | string | Идентификатор игрока |
| `Name` | string | Имя игрока |
| `Ready` | boolean | Готовность игрока |
| `Station` | Board | Игровая станция |
| `Inventory` | Inventory | Запасы ресурсов |
| `Robots` | Robot[] | Список роботов |
| `ProductionTasks` | ProductionTask[] | Производственные задачи |

Каждый игрок имеет собственную станцию и отдельный инвентарь.

Для определения своего игрока Frontend должен сравнивать `Player.ID` с идентификатором подключённого пользователя.

Не следует считать, что первый элемент массива `Players` всегда принадлежит текущему пользователю.

---

## 4.5. Board — игровая станция

| Поле | Тип | Описание |
|---|---|---|
| `Levels` | Level[] | Подземные уровни станции |
| `Surface` | Surface | Поверхность астероида |

### Level — уровень станции

| Поле | Тип | Описание |
|---|---|---|
| `Number` | number | Номер уровня |
| `Compartments` | Compartment[] | Отсеки уровня |

Всего предусмотрено восемь подземных уровней, по 21 отсеку на каждом.

### Surface — поверхность астероида

| Поле | Тип | Описание |
|---|---|---|
| `Level` | number | Номер поверхности |
| `Present` | boolean | Наличие поверхности |

Поверхность представлена отдельно от массива подземных уровней.

---

## 4.6. Compartment — отсек

| Поле | Тип | Описание |
|---|---|---|
| `ID` | string | Уникальный идентификатор отсека |
| `Level` | number | Номер уровня |
| `Position` | number | Позиция на уровне |
| `Type` | string | Тип отсека |
| `Damaged` | boolean | Состояние повреждения |

Возможные типы отсеков:

| Значение | Назначение |
|---|---|
| `unknown` | Тип ещё не определён |
| `production` | Производственный отсек |
| `combat` | Боевой отсек |
| `energy` | Энергетический отсек |
| `resource` | Ресурсный отсек |
| `rocket` | Ракетный отсек |
| `command` | Командный отсек |

Пример идентификатора:

```text
L1-C1
```

Он обозначает первый отсек первого уровня.

Frontend может использовать `ID` для выбора отсека, отображения его состояния и отправки запроса на ремонт.

---

## 4.7. Inventory — инвентарь

| Поле | Тип | Описание |
|---|---|---|
| `Metal` | number | Количество металла |
| `Uranium` | number | Количество урана |
| `Oxygen` | number | Количество кислорода |
| `Biomass` | number | Количество биомассы |
| `Energy` | number | Количество энергии |

Начальные тестовые значения:

| Ресурс | Количество |
|---|---:|
| Metal | 10 |
| Uranium | 5 |
| Oxygen | 10 |
| Biomass | 5 |
| Energy | 10 |

Frontend должен получать актуальные запасы с сервера, а не самостоятельно рассчитывать их после игровых действий.

---

## 4.8. Robot — робот

### Position — позиция

| Поле | Тип | Описание |
|---|---|---|
| `Level` | number | Уровень |
| `Position` | number | Позиция на уровне |

### Robot

| Поле | Тип | Описание |
|---|---|---|
| `ID` | string | Идентификатор робота |
| `OwnerID` | string | Идентификатор владельца |
| `Position` | Position | Текущая позиция |
| `Active` | boolean | Активен ли робот |

Роботы принадлежат игрокам и перемещаются в соответствии с результатом броска кубика.

Для перемещения Frontend передаёт серверу идентификатор робота и маршрут.

---

## 4.9. ProductionTask — производство

| Поле | Тип | Описание |
|---|---|---|
| `ID` | string | Идентификатор задачи |
| `Resource` | string | Тип производимого ресурса |
| `Amount` | number | Количество производимого ресурса |
| `RequiredTurns` | number | Необходимое количество ходов |
| `RemainingTurns` | number | Оставшееся количество ходов |
| `Completed` | boolean | Завершено ли производство |

Производственные задачи продвигаются после каждого завершённого хода игрока.

Frontend должен отображать состояние задачи на основании полученных от Backend данных.

---

## 4.10. Rocket — ракета

| Поле | Тип | Описание |
|---|---|---|
| `ID` | string | Идентификатор ракеты |
| `OwnerID` | string | Идентификатор владельца |
| `SourceStation` | string | Станция отправления |
| `TargetStation` | string | Станция назначения |
| `Position` | number | Текущая позиция ракеты |
| `TotalDistance` | number | Полная дистанция |
| `Speed` | number | Скорость |
| `Status` | string | Состояние ракеты |

Возможные состояния:

| Значение | Описание |
|---|---|
| `ready` | Готова к запуску |
| `flying` | Находится в полёте |
| `arrived` | Достигла цели |

Движение ракеты обновляется автоматически при продвижении игровых процессов.

---

## 4.11. RepairTask — ремонт

| Поле | Тип | Описание |
|---|---|---|
| `ID` | string | Идентификатор задачи |
| `OwnerID` | string | Идентификатор владельца |
| `CompartmentID` | string | Идентификатор ремонтируемого отсека |
| `RemainingTurns` | number | Оставшееся время ремонта |
| `Completed` | boolean | Завершён ли ремонт |

Предварительные параметры ремонта:

- стоимость — 2 металла;
- продолжительность — 2 игровых хода.

Эти значения могут быть изменены.

# 5. HTTP API

Все запросы выполняются относительно:

```text
http://localhost:8080
```

## 5.1. Проверка сервера

**Метод:** GET

**Маршрут:**

```http
/health
```

Назначение: проверка доступности Backend.

Ответ:

```json
{
  "status": "ok"
}
```

---

## 5.2. Получение списка комнат

**Метод:** GET

**Маршрут:**

```http
/api/rooms
```

Назначение:

- получить список существующих комнат;
- отобразить доступные комнаты;
- дать пользователю возможность выбрать комнату для подключения.

---

## 5.3. Создание комнаты

**Метод:** POST

**Маршрут:**

```http
/api/rooms
```

Тело запроса:

```json
{
  "PlayerID": "player-1",
  "PlayerName": "Player One"
}
```

Назначение:

1. Создать новую комнату.
2. Добавить первого игрока.
3. Вернуть созданную комнату.

Ответ содержит объект комнаты.

---

## 5.4. Получение комнаты

**Метод:** GET

**Маршрут:**

```http
/api/rooms/{id}
```

Пример:

```http
/api/rooms/room-1
```

Назначение:

- получить информацию о комнате;
- получить список игроков;
- получить состояние игровой партии, если она уже создана;
- обновить интерфейс игры.

Это основной запрос для получения актуального состояния игры.

---

## 5.5. Подключение к комнате

**Метод:** POST

**Маршрут:**

```http
/api/rooms/{id}/join
```

Тело запроса:

```json
{
  "PlayerID": "player-2",
  "PlayerName": "Player Two"
}
```

Назначение:

1. Подключить второго игрока.
2. Создать игровую партию.
3. Вернуть обновлённую информацию о комнате.

После подключения второго игрока комната переходит в состояние `playing`, если создание партии прошло успешно.

---

## 5.6. Бросок кубика

**Метод:** POST

**Маршрут:**

```http
/api/rooms/{id}/game/roll
```

Тело запроса:

```json
{
  "PlayerID": "player-1"
}
```

Ответ:

```json
{
  "Result": 4
}
```

Назначение:

- выполнить бросок кубика;
- получить случайный результат от Backend;
- сохранить результат в состоянии текущего хода.

Результат броска используется для игровых действий, которым требуется значение кубика.

Frontend не должен генерировать результат самостоятельно.

---

## 5.7. Завершение хода

**Метод:** POST

**Маршрут:**

```http
/api/rooms/{id}/game/end-turn
```

Тело запроса:

```json
{
  "PlayerID": "player-1"
}
```

Backend проверяет возможность завершения хода.

В текущей логике игрок должен:

1. Бросить кубик.
2. Выполнить основное действие.
3. Завершить ход.

После завершения хода Backend продвигает игровые процессы:

- перемещение ракет;
- производство ресурсов;
- ремонт отсеков.

Затем очередь переходит к следующему игроку.

---

## 5.8. Перемещение робота

**Метод:** POST

**Маршрут:**

```http
/api/rooms/{id}/game/move-robot
```

Тело запроса:

```json
{
  "PlayerID": "player-1",
  "RobotID": "robot-1",
  "Path": [
    {
      "Level": 1,
      "Position": 1
    },
    {
      "Level": 1,
      "Position": 2
    },
    {
      "Level": 1,
      "Position": 3
    },
    {
      "Level": 1,
      "Position": 4
    },
    {
      "Level": 1,
      "Position": 5
    }
  ]
}
```

Назначение:

- указать робота, которым необходимо управлять;
- передать маршрут;
- выполнить перемещение на основании результата кубика.

Важно:

- маршрут передаётся Frontend;
- Backend определяет фактическое перемещение с учётом результата кубика;
- текущая реализация ещё не обеспечивает полную проверку допустимости маршрута по игровому полю.

Frontend не должен считать локальную проверку маршрута полноценной серверной проверкой.

---

## 5.9. Начало ремонта

**Метод:** POST

**Маршрут:**

```http
/api/rooms/{id}/game/repair
```

Тело запроса:

```json
{
  "PlayerID": "player-1",
  "TaskID": "repair-1",
  "CompartmentID": "L1-C1"
}
```

Назначение:

- указать ремонтируемый отсек;
- создать задачу ремонта;
- списать необходимое количество ресурсов;
- начать отсчёт времени ремонта.

Предварительные параметры:

| Параметр | Значение |
|---|---:|
| Стоимость металла | 2 |
| Продолжительность | 2 хода |

После завершения ремонта Backend обновляет состояние отсека.

# 7. Как Frontend должен работать с состоянием игры

## 7.1. Получение состояния

После создания комнаты, подключения к ней или выполнения игрового действия Frontend должен получить актуальное состояние комнаты.

Основной запрос:

```http
GET /api/rooms/{id}
```

Полученный объект содержит данные комнаты и, если партия создана, состояние игры.

## 7.2. Определение текущего игрока

Frontend должен сравнивать идентификатор текущего пользователя с идентификатором игрока, указанным в состоянии хода.

Логика:

```ts
const isMyTurn =
  currentPlayerID === myPlayerID;
```

## 7.3. Проверка возможности бросить кубик

Кубик можно бросить, если:

- сейчас ход данного игрока;
- кубик ещё не был брошен.

```ts
const canRollDice =
  isMyTurn && !diceRolled;
```

## 7.4. Проверка возможности выполнить действие

Основное действие можно выполнить, если:

- сейчас ход данного игрока;
- кубик уже брошен;
- основное действие ещё не использовано.

```ts
const canPerformAction =
  isMyTurn &&
  diceRolled &&
  !actionUsed;
```

## 7.5. Проверка возможности завершить ход

Ход можно завершить, если:

- сейчас ход данного игрока;
- кубик уже брошен;
- основное действие использовано.

```ts
const canEndTurn =
  isMyTurn &&
  diceRolled &&
  actionUsed;
```

Эти проверки нужны для управления интерфейсом. Они не заменяют проверки Backend.

# 8. Рекомендуемая структура Frontend

Предлагаемая организация Frontend:

```text
frontend/
│
├── src/
│   │
│   ├── api/
│   │   ├── client.ts
│   │   ├── rooms.ts
│   │   └── game.ts
│   │
│   ├── types/
│   │   ├── room.ts
│   │   ├── game.ts
│   │   ├── player.ts
│   │   ├── board.ts
│   │   ├── robot.ts
│   │   ├── rocket.ts
│   │   └── resources.ts
│   │
│   ├── components/
│   │
│   ├── pages/
│   │
│   ├── hooks/
│   │
│   ├── utils/
│   │
│   └── App.tsx

```

Это рекомендуемая структура, а не обязательное требование.

| `types/resources.ts` | Типы ресурсов и производственных задач |

# 9. Пример общего API-клиента

Для работы с сервером рекомендуется использовать одну общую функцию запросов.

Пример реализации:

```ts
const API_URL = "http://localhost:8080";

export async function apiRequest<T>(
  endpoint: string,
  options: RequestInit = {}
): Promise<T> {
  const response = await fetch(
    `${API_URL}${endpoint}`,
    {
      ...options,
      headers: {
        "Content-Type": "application/json",
        ...options.headers,
      },
    }
  );

  const data = await response.json();

  if (!response.ok) {
    throw new Error(
      data.error ||
      data.Error ||
      "Ошибка запроса к серверу"
    );
  }

  return data as T;
}
```

Пример GET-запроса:

```ts
const room = await apiRequest<Room>(
  `/api/rooms/${roomID}`
);
```

Пример POST-запроса:

```ts
const room = await apiRequest<Room>(
  "/api/rooms",
  {
    method: "POST",
    body: JSON.stringify({
      PlayerID: playerID,
      PlayerName: playerName,
    }),
  }
);
```

Важно: TypeScript-типы не проверяют JSON во время выполнения. Если сервер вернул данные другого формата, простое приведение `as T` не исправит их структуру.

# 10. Обновление игрового состояния

На текущем этапе WebSocket не реализован.

Для обновления состояния игры рекомендуется использовать периодические GET-запросы.

Например:

```ts
async function updateRoom(roomID: string) {
  return await apiRequest<Room>(
    `/api/rooms/${roomID}`
  );
}
```

Рекомендуемая схема:

1. Frontend получает состояние комнаты.
2. Отображает игровое поле.
3. Игрок выполняет действие.
4. Frontend отправляет POST-запрос.
5. Backend обрабатывает действие.
6. Frontend повторно получает состояние комнаты.
7. Интерфейс обновляется.

Для отображения действий второго игрока можно периодически запрашивать состояние комнаты с интервалом примерно 1–2 секунды.

В дальнейшем polling можно заменить на WebSocket.

# 11. Обработка ошибок

Backend возвращает ошибки в JSON.

Предполагаемый общий формат:

```json
{
  "Error": "описание ошибки"
}
```

При этом точное имя поля зависит от JSON-тега структуры `ErrorResponse`. Если тег не указан, стандартная сериализация Go использует имя `Error`.

Frontend должен:

- проверять HTTP-статус ответа;
- читать сообщение об ошибке;
- показывать понятное уведомление пользователю;
- не изменять локальное состояние игры, если сервер отклонил действие;
- после ошибки при необходимости повторно запрашивать состояние комнаты.

Основные ситуации, которые необходимо обрабатывать:

- комната не найдена;
- игрок не найден;
- сейчас ход другого игрока;
- кубик уже брошен;
- кубик ещё не брошен;
- основное действие уже использовано;
- недостаточно ресурсов;
- отсек не найден;
- отсек не нуждается в ремонте;
- некорректные параметры запроса.

Это примеры игровых ошибок, а не гарантированный исчерпывающий перечень HTTP-кодов для каждой ситуации.

# 12. Что пока не доступно через HTTP API

Внутри Backend уже предусмотрена часть игровой логики, которая пока не имеет отдельных HTTP-маршрутов.

На текущем этапе необходимо учитывать следующие ограничения:

| Возможность | Состояние |
|---|---|
| Создание комнаты | Реализовано |
| Подключение второго игрока | Реализовано |
| Получение комнаты | Реализовано |
| Получение списка комнат | Реализовано |
| Бросок кубика | Реализовано |
| Завершение хода | Реализовано |
| Перемещение робота | Реализовано |
| Начало ремонта | Реализовано |
| Добавление робота через HTTP | Пока не реализовано |
| Запуск производства через HTTP | Пока не реализовано |
| Получение произведённых ресурсов через HTTP | Пока не реализовано |
| Запуск ракеты через HTTP | Пока не реализовано |
| WebSocket | Пока не реализовано |
| Авторизация | Пока не реализована |
| Постоянное хранение партий | Пока не реализовано |

Наличие метода во внутреннем Go-коде не означает, что Frontend уже может вызвать его через HTTP.

Для добавления нового игрового действия необходимо реализовать соответствующий HTTP-маршрут и описать его здесь.

# 13. Правила взаимодействия с Backend

При разработке Frontend необходимо соблюдать следующие правила:

1. Не изменять игровые данные только на стороне Frontend.
2. Не генерировать результат броска кубика самостоятельно.
3. Не считать локальные проверки достаточной защитой от неправильных действий.
4. Не предполагать, что ход принадлежит текущему пользователю.
5. Не привязывать своего игрока к фиксированному индексу массива.
6. После выполнения действия получать актуальное состояние с сервера.
7. Обрабатывать ошибки HTTP-запросов.
8. Не обращаться к внутренним Go-файлам напрямую — использовать HTTP API.
9. Не считать внутренние методы Backend доступными, если для них не создан HTTP-маршрут.
10. При изменении формата API согласовывать изменения с Backend-разработчиком и обновлять этот документ.

# 14. Изменение контракта

Если Backend-разработчик меняет:

- название или тип поля;
- структуру игрового объекта;
- HTTP-маршрут;
- формат запроса;
- формат ответа;
- правила выполнения действия;
- возможные состояния игрового объекта;

то соответствующие изменения должны быть внесены в этот документ.

Frontend-разработчик должен использовать актуальную версию контракта.

**Главный принцип:** Frontend и Backend должны работать с одинаковыми структурами данных и одинаковыми правилами взаимодействия.
