# Septikon Online — Backend

## 1. О проекте

**Septikon Online** — браузерная многопользовательская пошаговая игра по мотивам настольной игры «Септикон».

Проект разрабатывается на Go. Backend отвечает за игровую логику, состояние игровых комнат, обработку действий игроков и передачу данных Frontend через HTTP API.

Frontend отвечает за отображение игрового поля, интерфейс игроков, визуализацию игровых объектов и отправку запросов на Backend.

Этот документ описывает текущую структуру Backend и помогает разработчикам ориентироваться в проекте.

## 2. Технологии

- **Go** — язык Backend.
- **HTTP** — взаимодействие Frontend и Backend.
- **JSON** — формат передачи данных.
- **TypeScript** — рекомендуемый язык для Frontend.

## 4. Запуск Backend

Для запуска проекта необходимо установить Go и открыть терминал в корневой папке проекта.

Запуск сервера:

```bash
go run ./cmd/server
```

По умолчанию сервер использует порт `8080`.

Адрес:

```text
http://localhost:8080
```

### Проверка работы сервера

```http
GET /health
```

Ожидаемый ответ:

```json
{
  "status": "ok"
}
```

### Запуск тестов

```bash
go test ./...
```

Эта команда запускает тесты всех пакетов проекта.

## 5. Основные игровые правила

На текущем этапе согласованы следующие базовые правила:

- В одной партии участвуют два игрока.
- У каждого игрока есть собственная космическая станция.
- Игроки выполняют действия по очереди.
- За один ход можно выполнить одно основное действие.
- За один ход можно один раз бросить кубик.
- Роботы перемещаются на количество клеток, определяемое результатом броска.
- Ракеты перемещаются автоматически.
- Производство ресурсов занимает определённое количество игровых ходов.
- Ремонт повреждённых отсеков также занимает время.
- Игровые процессы обновляются после завершения каждого отдельного хода игрока.

Последнее правило важно: производство, ремонт и перемещение ракет продвигаются после хода каждого игрока, а не после полного круга из двух игроков.

## 6. Игровое поле

Станция состоит из восьми подземных уровней и поверхности астероида.

| Элемент | Количество |
|---|---:|
| Подземные уровни | 8 |
| Отсеков на одном уровне | 21 |
| Всего подземных отсеков | 168 |
| Поверхность | 1 |

Каждый отсек имеет:

- уникальный идентификатор;
- номер уровня;
- позицию на уровне;
- тип;
- состояние повреждения.

Пример идентификатора отсека:

```text
L1-C1
```

Он обозначает первый отсек первого уровня.

Поверхность астероида представлена отдельным объектом `Surface`.

## 7. Ресурсы

В игре предусмотрено пять основных ресурсов.

| Название в Backend | Назначение |
|---|---|
| `Metal` | Металл, используется для ремонта и других игровых операций |
| `Uranium` | Уран |
| `Oxygen` | Кислород |
| `Biomass` | Биомасса |
| `Energy` | Энергия |

Начальные тестовые запасы одного игрока:

| Ресурс | Количество |
|---|---:|
| Metal | 10 |

| Oxygen | 10 |
| Biomass | 5 |

Эти значения являются начальными настройками текущей версии и могут измениться.

## 8. Основные игровые объекты

### Room

Игровая комната. Содержит идентификатор, статус, список подключённых игроков и игровую партию, если она уже создана.

### Game

Игровая партия. Содержит игроков, ракеты, статус игры, менеджер ходов и информацию о победителе.

### Player

Игрок. Содержит имя, идентификатор, готовность, собственную станцию, инвентарь, роботов и производственные задачи.

### Board

Игровая станция. Содержит уровни и поверхность астероида.

### Compartment

Отсек станции. Имеет тип, положение и состояние повреждения.

### Robot

Робот, принадлежащий игроку. Имеет идентификатор, владельца, позицию и состояние активности.

### Rocket

Ракета, которая перемещается между станциями. Содержит отправителя, получателя, скорость, дистанцию и текущий статус.

### ProductionTask

Задача производства ресурса. Содержит производимый ресурс, количество и оставшееся время.

### RepairTask

Задача ремонта повреждённого отсека. Содержит владельца, идентификатор отсека и оставшееся время ремонта.

## 9. Текущие игровые действия

На уровне игровой логики предусмотрены:

- бросок кубика;
- добавление робота;
- перемещение робота;
- запуск производства;
- получение произведённых ресурсов;
- запуск ракеты;
- продвижение игровых процессов;
- начало ремонта;
- завершение ремонта;
- завершение хода.

Не все эти действия на данный момент доступны через HTTP API. Список доступных HTTP-маршрутов приведён в `frontend-contract.md`.

## 10. HTTP API

Базовый адрес:

```text
http://localhost:8080
```

Текущие маршруты:

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/health` | Проверка работоспособности сервера |
| GET | `/api/rooms` | Получение списка комнат |
| POST | `/api/rooms` | Создание комнаты |
| GET | `/api/rooms/{id}` | Получение информации о комнате |
| POST | `/api/rooms/{id}/join` | Подключение к комнате |
| POST | `/api/rooms/{id}/game/roll` | Бросок кубика |
| POST | `/api/rooms/{id}/game/end-turn` | Завершение хода |
| POST | `/api/rooms/{id}/game/move-robot` | Перемещение робота |
| POST | `/api/rooms/{id}/game/repair` | Начало ремонта |

Подробные параметры запросов и описание взаимодействия с API находятся в `frontend-contract.md`.

## 11. Хранение данных

На текущем этапе игровые комнаты хранятся в оперативной памяти сервера.

Это означает:

- после перезапуска сервера игровые комнаты удаляются;
- постоянная база данных пока не используется;
- состояние комнаты доступно через менеджер комнат.

## 12. Ограничения текущей версии

- Пока нет полноценной авторизации пользователей.
- Пока нет постоянного хранения игровых партий.
- WebSocket ещё не реализован.
- Для обновления состояния игры Frontend может использовать периодические GET-запросы.
- Проверка допустимости маршрутов роботов требует дальнейшего развития.
- Не все игровые действия доступны через HTTP API.
- Условия победы и некоторые игровые параметры ещё требуют окончательного согласования.

## 13. Взаимодействие Backend и Frontend

Backend является источником истины для состояния игры.

Frontend должен:

1. Отправлять запросы на Backend.
2. Получать актуальное состояние комнаты.
3. Отображать состояние игры.
4. Отправлять выбранные игроком действия.
5. Обрабатывать ответы и ошибки сервера.
6. Обновлять интерфейс после изменения состояния игры.

Frontend не должен самостоятельно изменять игровое состояние, рассчитывать окончательный результат действия или считать локальную проверку правил заменой проверкам Backend.

## 14. Документация API

Для работы с Backend Frontend-разработчику необходимо использовать:

**`frontend-contract.md`**

В нём описаны:

- структура игровых объектов;
- поля и их назначение;
- HTTP-маршруты;
- форматы запросов;
- форматы ответов;
- правила выполнения игровых действий;
- обработка ошибок;
- порядок обновления состояния игры.

При изменении Backend необходимо обновлять оба документа, чтобы документация соответствовала реальной реализации.
